১. Node.js Core & Architecture (Deep Dive)
ক. The Event Loop, libuv & Thread Pool:

কীভাবে কাজ করে: Node.js সিঙ্গল-থ্রেডেড (V8 ইঞ্জিন)। কিন্তু এর পেছনে থাকা C++ লাইব্রেরি libuv মাল্টি-থ্রেডিংয়ের কাজ করে।

Thread Pool: Node.js-এর ডিফল্ট Thread Pool-এ ৪টি থ্রেড থাকে (আপনি চাইলে UV_THREADPOOL_SIZE দিয়ে বাড়াতে পারেন)। যখন আপনি কোনো ভারী কাজ দেন (যেমন- fs.readFile, crypto.pbkdf2, বা DNS lookup), তখন Event loop সেটা এই Thread Pool-এ পাঠিয়ে দেয়।

Event Loop Phases:

Timers: setTimeout, setInterval রান করে।

Poll: নতুন I/O ইভেন্ট (ফাইল রিড, নেটওয়ার্ক রিকোয়েস্ট) রিসিভ করে।

Check: setImmediate() রান করে।

ইন্টারভিউ ট্রিক প্রশ্ন (setImmediate vs setTimeout(0)):

উত্তর: যদি সাধারণ স্ক্রিপ্টে রান করেন, তবে কে আগে রান করবে তার গ্যারান্টি নেই। কিন্তু যদি কোনো I/O সাইকেলের ভেতরে (যেমন fs.readFile-এর কলব্যাকে) রান করেন, তবে setImmediate সবসময় আগে রান করবে কারণ Poll ফেজের ঠিক পরেই Check ফেজ আসে।

খ. Streams & Backpressure:

কেন লাগে: ১ জিবি ফাইল একবারে মেমরিতে আনলে RAM ক্র্যাশ করবে (Out of Memory)। Stream ডেটাকে ছোট ছোট চাঙ্কে (Buffer) ভাগ করে পাঠায়।

Backpressure কী: ধরুন আপনি ডাটাবেস থেকে খুব দ্রুত ডেটা রিড করছেন, কিন্তু ক্লায়েন্টের কাছে নেটওয়ার্ক দিয়ে পাঠাতে (Write) সময় লাগছে। একসময় রাইটারের বাফার ফুল হয়ে যাবে। তখন write() মেথড false রিটার্ন করে। একেই Backpressure বলে।

কীভাবে সামলাবেন: write() ফলস দিলে ডেটা রিড করা pause() করতে হবে। রাইটারের বাফার খালি হলে সে একটি 'drain' ইভেন্ট ফায়ার করবে। তখন আবার resume() করতে হবে।

গ. Graceful Shutdown:

কী এবং কেন: হুট করে সার্ভার বন্ধ (Crash/Ctrl+C) করলে ইউজারের ট্রানজেকশন মাঝপথে আটকে যেতে পারে।

সিস্টেম:

process.on('SIGTERM', callback) লিসেন করতে হবে।

server.close() কল করতে হবে (যাতে নতুন রিকোয়েস্ট না আসে)।

চলমান API রিকোয়েস্ট শেষ হওয়া পর্যন্ত অপেক্ষা করতে হবে।

ডাটাবেস কানেকশন (mongoose.disconnect(), pg.end()) ক্লোজ করতে হবে।

সবশেষে process.exit(0) করতে হবে।

২. Database Engineering (PostgreSQL + MongoDB)
ক. Concurrency & Locking (Race Conditions ঠেকানো):

Optimistic Locking (MongoDB): এখানে আসলে ডেটাবেস লক হয় না। আমরা কন্ডিশন দিয়ে আপডেট করি।

কীভাবে: ইউজারের অ্যাকাউন্টে ১০০ টাকা আছে। সে ২০০ টাকা তুলতে চাইলো। আপনি কোয়েরি লিখবেন: findOneAndUpdate({ _id, balance: { $gte: 200 } }, { $inc: { balance: -200 } })। যদি তার ব্যালেন্স ২০০ এর নিচে নেমে যায়, কোয়েরিটি কাজ করবে না (null রিটার্ন করবে)।

আরেকটি প্যাটার্ন: ডেটাতে একটি version ফিল্ড রাখা। আপডেট করার সময় version: currentVersion চেক করা এবং আপডেট হলে version + 1 করে দেওয়া।

Pessimistic Locking (PostgreSQL): এখানে ডেটাবেসের Row আসলেই লক করে দেওয়া হয়।

কীভাবে: SELECT * FROM wallets WHERE user_id = 1 FOR UPDATE;

প্রভাব: এই ট্রানজেকশন শেষ (Commit/Rollback) না হওয়া পর্যন্ত অন্য কোনো রিকোয়েস্ট এই ইউজারের ব্যালেন্স রিড বা রাইট করতে পারবে না, তাদেরকে লাইনে দাঁড়িয়ে অপেক্ষা করতে হবে।

বিপদ (Deadlock): প্রসেস A লক করেছে টেবিল ১, প্রসেস B লক করেছে টেবিল ২। এখন A চাচ্ছে ২ কে, আর B চাচ্ছে ১ কে। দুজনেই অনন্তকাল বসে থাকবে। একে Deadlock বলে।

খ. Indexing Rules:

ESR Rule (MongoDB): Equality -> Sort -> Range.

যদি কোয়েরি হয়: find({ status: 'VIP', points: { $gt: 100 } }).sort({ joinedAt: 1 })

ইনডেক্স বানাতে হবে: { status: 1, joinedAt: 1, points: 1 } (প্রথমে exact match, তারপর sort, শেষে range filter)।

B-Tree vs GIN (PostgreSQL):

B-Tree ডিফল্ট ইনডেক্স। নাম্বার বা টেক্সট সার্চের জন্য বেস্ট।

GIN (Generalized Inverted Index) স্পেশালভাবে ব্যবহার হয় JSONB কলামের ভেতরে কোনো নির্দিষ্ট কি-ভ্যালু বা Array এলিমেন্ট দ্রুত খোঁজার জন্য।

গ. N+1 Problem:

সমস্যা: আপনি ১০ জন ইউজারের লিস্ট ডাটাবেস থেকে আনলেন (১টি কোয়েরি)। এরপর লুপ চালিয়ে প্রত্যেক ইউজারের প্রোফাইল পিকচার আনার জন্য ডাটাবেসকে কল করলেন (১০টি কোয়েরি)। মোট কোয়েরি হলো ১+১০ = ১১টি। ইউজার ১০০০ হলে কোয়েরি হবে ১০০১টি। সিস্টেম স্লো হয়ে যাবে।

সমাধান: লুপের ভেতর কোয়েরি না করে, সবার আইডি একটা Array তে নিয়ে WHERE user_id IN (1,2,3...) দিয়ে মাত্র ১টি এক্সট্রা কোয়েরিতে সব ডেটা নিয়ে আসা। (GraphQL-এ এর জন্য DataLoader ব্যবহার করা হয়)।

৩. System Design & Scalability
ক. Message Queues (RabbitMQ / Kafka):

কেন লাগে: ডাটাবেসের Write ক্যাপাসিটি লিমিটেড। একসাথে ১০,০০০ ইউজার পেমেন্ট রিকোয়েস্ট দিলে ডাটাবেস ক্র্যাশ করবে।

কীভাবে কাজ করে: API সরাসরি ডাটাবেসে না গিয়ে রিকোয়েস্টগুলোকে Queue (লাইনে) রেখে দেয়। API সাথে সাথে ইউজারকে বলে দেয় "Processing"। পেছনে থাকা Worker সার্ভারগুলো নিজেদের স্পিড অনুযায়ী Queue থেকে একটা একটা করে রিকোয়েস্ট নিয়ে ডাটাবেসে সেভ করে।

Dead Letter Queue (DLQ): ধরুন একটা রিকোয়েস্টের ডেটা ভুল, Worker সেটা ৩ বার ডাটাবেসে সেভ করার ট্রাই করে ফেইল করলো। তখন সেটা ডিলিট না করে DLQ-তে পাঠিয়ে দেওয়া হয়। পরে ডেভেলপাররা লগ চেক করে সেটা ম্যানুয়ালি ফিক্স করতে পারে। এতে ইউজারের ১ টাকাও হারায় না।

খ. Pagination (Offset vs Cursor):

Offset (খারাপ পদ্ধতি): SELECT * FROM tx LIMIT 20 OFFSET 10000; ডাটাবেসকে প্রথম ১০,০০০ ডেটা গুণে গুণে মেমরিতে আনতে হয়, তারপর সেগুলোকে ফেলে দিয়ে পরের ২০টা দিতে হয়। পেজ যত পেছনে যাবে, ডাটাবেস তত স্লো হবে O(N)।

Cursor (ভালো পদ্ধতি): SELECT * FROM tx WHERE id > 'last_seen_id' LIMIT 20; এটি ইনডেক্স ব্যবহার করে সরাসরি ওই আইডিতে লাফ দেয়। O(1) স্পিড।

গ. Caching (Redis):

Cache-Aside Pattern: প্রথমে অ্যাপ Redis-এ খোঁজে। পেলে রিটার্ন করে (Cache Hit)। না পেলে ডাটাবেস থেকে আনে (Cache Miss), তারপর ইউজারকে দেওয়ার আগে Redis-এ সেভ করে রাখে।

Cache Stampede: ধরুন একটা খুব পপুলার ক্যাশের মেয়াদ (TTL) শেষ হলো। ঠিক সেই মাইক্রোসেকেন্ডে ১০০০ ইউজার রিকোয়েস্ট করলো। সবাই দেখবে ক্যাশ খালি, ফলে ১০০০ রিকোয়েস্ট একসাথে মেইন ডাটাবেসে গিয়ে আছড়ে পড়বে।

সমাধান: Mutual Exclusion (Mutex) Lock ব্যবহার করা। প্রথম যে রিকোয়েস্ট ক্যাশ মিস খাবে, সে একটা লক তৈরি করবে। বাকি ৯৯৯ জন অপেক্ষা করবে। প্রথম জন ডাটাবেস থেকে এনে ক্যাশে রাখার পর বাকিরা ক্যাশ থেকে ডেটা পাবে।

৪. Security & API Design
ক. Idempotency (সবচেয়ে ইম্পর্ট্যান্ট API কনসেপ্ট):

সমস্যা: ইউজার পেমেন্ট বাটনে ক্লিক করলো। রিকোয়েস্ট সার্ভারে গিয়ে ইউজারের টাকা কাটলো। কিন্তু ইউজারের ইন্টারনেট স্লো থাকায় তার কাছে কনফার্মেশন পৌঁছালো না। ইউজার ভাবলো পেমেন্ট হয়নি, সে আবার ক্লিক করলো। আবার টাকা কেটে নিলো!

সমাধান: ফ্রন্টএন্ড থেকে রিকোয়েস্টের হেডারে একটি Idempotency-Key (UUID) পাঠাতে হবে। ব্যাকএন্ড প্রথমে চেক করবে এই Key দিয়ে আগে কোনো কাজ হয়েছে কি না (ডাটাবেস বা Redis-এ)। যদি হয়ে থাকে, তবে নতুন করে প্রসেস না করে সরাসরি আগের সাকসেস মেসেজটি পাঠিয়ে দেবে।

খ. ACID Properties (PostgreSQL):
আর্থিক লেনদেনে রিলেশনাল ডাটাবেস কেন মাস্ট, তার কারণ হলো ACID:

A (Atomicity): ট্রানজেকশনের ভেতরে ৩টা কুয়েরি থাকলে ৩টাই পাস হতে হবে, অথবা একটা ফেইল করলে আগেরগুলো রোলব্যাক (Rollback) হয়ে আগের অবস্থায় ফিরে যাবে।

C (Consistency): ডাটাবেসের রুলস (যেমন- ব্যালেন্স কখনো মাইনাস হবে না) সব সময় ঠিক থাকবে।

I (Isolation): একসাথে একাধিক ট্রানজেকশন ঘটলে একটা আরেকটার ডেটায় নাক গলাবে না (Row locks)।

D (Durability): একবার কমিট (Commit) হয়ে গেলে সার্ভারের কারেন্ট চলে গেলেও ডেটা হারাবে না।
